# معالجة طلبات العملاء بالنموذج المحلي

## نطاق الخدمة

يخدم هذا التطبيق العملاء ومستخدمي الأجهزة الطبية، بما في ذلك العملاء الداخليون من كوادر المنشأة. الطلبات المدعومة هي الأعطال، والإنذارات، ومشكلات تشغيل جهاز مسجل. لا يشمل النطاق العام المشتريات أو الحسابات أو الدعم التقني لأجهزة غير طبية، ولا تشخيص المرضى أو وصف العلاج. اقتراح النطاق أولي ويمكن للمستخدم توضيح الطلب وإعادة تحليله.

## دور النموذج وطريقة التشغيل

لا يحتاج المستخدم إلى مفتاح API أو حساب عند مزود نموذج، ولا تُضاف خدمة مدفوعة. بعد الدخول إلى حساب التطبيق المعتاد، يختار الجهاز ويكتب وصف المشكلة ثم يضغط «التحقق والتحليل». يبقى النموذج المحلي مفعّلًا افتراضيًا. التنزيل الأول يشمل الأوزان وملفات التشغيل؛ الاستدلال التالي يجري على جهاز المستخدم عندما تبقى الملفات في ذاكرة المتصفح المؤقتة.

أصبح للنموذج استدلالان متتاليان باستخدام الجلسة نفسها: تصنيف وصف العطل إلى فئة فنية، ثم اقتراح المرجع الموافق للأعراض أو الامتناع عن اختيار حل. لا يُنشأ نص إصلاح حر. تُستخرج الإجابة الفنية، ومصدرها وصفحتها، وإجراءات التحقق من سجل المرجع الذي اختاره النموذج وقبله الخادم. هذا استخدام للنموذج في اختيار حل مرجعي، وليس دليلًا على إصلاح الجهاز ماديًا أو على صحة الاقتراح.

التخصيص هنا تعليمات وأمثلة ثابتة ومخرجات مقيدة، وليس تدريبًا أو ضبطًا دقيقًا لأوزان النموذج. لا توجد قاعدة متجهات أو خدمة استدلال سحابية في هذا المسار.

## سير البيانات

1. يرسل التطبيق وصف الطلب إلى `POST /api/intelligent-support/prepare-support` باستخدام تسجيل الدخول الموجود.
2. يأخذ الخادم هوية الجهاز ومصنعه وموديله من قاعدة البيانات، ويتجاهل بيانات الهوية الظاهرية التي يمكن للعميل تعديلها.
3. تُرشّح ثلاثة مراجع بحد أقصى، وفق المطابقة النصية القائمة وحدها الأدنى 0.58. يشترط تطابق نوع الجهاز والمصنع والموديل، أو الاسم المطابق عند غياب بيانات المصنع/الموديل، ووجود مصدر ورابط HTTPS وحل وسجل موسوم `VERIFIED_MANUFACTURER`. وسم السجل لا يثبت تدقيق كل صفحة مصدر خلال هذا التعديل.
4. يحصل النموذج على وصف الطلب المنقح واسم الجهاز وملخصات أعراض المراجع. لا تُعطى له هوية مقدم الطلب أو الرقم التسلسلي أو الموقع.
5. عند وجود مرشحين يختار النموذج A–C للمرجع المعروض أو D عند نقص التفاصيل. وعند غياب المرشحين يستخدم توجيه النطاق للاختيار بين D (طلب فني يحتاج تفاصيل/مرجعًا) وE (خارج نطاق الدعم). يسبق الرمز تمهيد مساعد ثابت `{"choice":"`؛ يُولد رمز واحد فقط، وليس كائن JSON أو نص إصلاح. يُقبل الرمز المنفرد مع مسافة بادئة اختيارية، ثم يحوّل إلى الحرف القياسي. قناع الرموز يستبعد أي مرجع غير معروض. التقييد لا يضمن صحة الاختيار.
6. يُرسل الاقتراح في `browser_llm.support` مع الإصدار وبصمة السياق والزمن. يعيد الخادم حساب قائمة المراجع والبصمة من بياناته الحالية، بما فيها النص الكامل للمراجع وسياق الجهاز والخبرة واتصال المريض. تغير المرجع أو الطلب يجعل النتيجة قديمة وغير مقبولة.
7. إذا كان التصنيف الأول غير واضح، لا يسمح الخادم بتمرير اختيار مرجع كحل؛ يطلب التوضيح. عند امتناع النموذج أو رفض السياق تُحجب أيضًا نتائج الاسترجاع الثانوي، حتى لا يتجاوز مسار آخر الامتناع.
8. تبقى خطورة القواعد وخطورة المرجع الأول حدًا أدنى حتى إذا اقترح النموذج مرجعًا أقل خطورة أو اعتبر الطلب خارج النطاق. للطوارئ أولوية الإحالة السريرية دائمًا.
9. يُحفظ القرار الخام ومعرف المرجع والمصادر وإصدار التوجيه وبصمته ضمن سجل المراجعة نفسه. يبقى اعتماد الحل أو تعديله أو إحالته قرارًا للمختص.

## ما يراه العميل

| الحالة | النتيجة |
|---|---|
| `SELECTED` | مرجع اختاره النموذج، مع نص الحل والمصدر ومراجعة المختص |
| `NEEDS_DETAILS` | أسئلة عن رمز الإنذار والأعراض وهوية الجهاز وزر لاستكمال الوصف |
| `NO_REFERENCE` | لا يوجد اختيار مرجعي مناسب؛ توضيح الطلب ومراجعة مهندس الأجهزة الطبية |
| `OUT_OF_SCOPE` | توضيح نطاق الخدمة وإمكانية إعادة وصف الطلب |
| `FALLBACK` | نتيجة البحث المرجعي مع تصريح بأن النموذج لم يشارك في اختيار الحل |
| `INVALID_RESULT` | اقتراح لا يطابق السياق الحالي أو يختار مرجعًا غير معروض؛ يُرفض |

فشل التحميل أو إلغاء الانتظار لا يستدعي OpenAI أو Groq تلقائيًا. عند فشل تجهيز المراجع يمكن أن يستمر تصنيف الفئة وحده، وتظهر نتيجة الاختيار كعودة إلى القواعد. لا تُنسب درجة المطابقة النصية إلى ثقة النموذج أو دقته.

## حدود الإثبات والتقييم

بصمة السياق تكشف البيانات القديمة لكنها لا تثبت أن متصفحًا غير موثوق قد شغّل النموذج فعلًا؛ يستطيع عميل معدل اصطناع النتيجة. لذلك يبقى السجل موسومًا `client_reported`، ولا يصلح وحده لإثبات تجربة علمية. التحقق التجريبي المستقل يتطلب أوصافًا موسومة من خبراء، وحالات خارج النطاق، وتحليل الأخطاء والامتناع والوقت، وتقييم ملاءمة الحل ومصدره واعتماد المختص.

اختبارات الوحدة تتحقق من صحة الربط ورفض البيانات غير الصالحة، ولا تقيس دقة الفهم. ملفات `supportSmokeCases.json` حالات تطوير اصطناعية استُخدمت أثناء ضبط التوجيه، وليست مجموعة اختبار مستقلة. يمكن إعادة الاستدلال الفعلي بواسطة:

```bash
cd frontend
npm ci
npm run smoke:llm:support
npm run smoke:llm:wasm
```

صفحة `/local-model` عامة وتتيح تجربة التصنيف أو اختيار المرجع بأمثلة اصطناعية فقط. لا تنشئ بلاغًا ولا ترسل الأمثلة إلى API التطبيق. الصفحة لا تعرض تعليمات إصلاح مستمدة من المراجع الاصطناعية.

## ملاحظات اختيار النموذج أثناء التطوير

جرى اختبار صيغ مختلفة للتوجيه وأوزان أخرى. أظهرت الصيغ الأولى أخطاء في اختيار مرجع لوصف عربي وفي الامتناع عند الوصف الغامض. نجحت نسخة Qwen2.5‑1.5B q4 في حالات الاختيار الست على CPU، لكنها فشلت في التحميل عبر WASM في بيئة الاختبار؛ لذلك لم تُعتمد. كما لم تحقق تجارب النسخ q8 وQwen2.5‑0.5B نتائج مناسبة للوظيفتين معًا. بقي النموذج المنشور Qwen3‑0.6B q4، مع توجيه منفصل للنطاق وتمهيد ثابت لاختيار المرجع. هذه تجارب تطوير وصياغة توجيه، ولا تسمح باستنتاج تفوق عام لنموذج على آخر.
