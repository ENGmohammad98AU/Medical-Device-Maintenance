# تجهيز النموذج وميزانية الاستجابة

## ما الذي تغيّر؟

كان أول طلب يعيد حساب نحو 730 رمزًا ثابتًا للتصنيف ونحو 455 رمزًا لاختيار المرجع. يسجّل القياس السابق في `evaluation/qwen17-runtime-speed-20260926.json` نحو 216 ثانية لأول طلب، رغم انخفاض الطلبات الدافئة إلى 14–23 ثانية. وكان تبديل المهمة إلى التحقق من النطاق بلا مراجع ينافس القالبين على موقعين فقط في ذاكرة السياق.

أصبح زر «تجهيز النموذج مسبقًا» متاحًا في الصيانة وتقارير الأعطال وصفحة التجربة. ينزّل الأوزان عند الحاجة، ثم يجهز القوالب الثابتة الثلاثة بمدخلات اصطناعية فارغة، قبل إرسال أي بلاغ. لا تُحفظ مخرجات هذا التجهيز كبلاغ أو نتيجة تحليل. تستخدم النسخة ثلاثة مواقع للسياق، مجموعها 4608 رموز (1536 لكل موقع)، مع بقاء سقف الإدخال المقبول 1024 وعدم السماح باقتطاع السياق. لم يتغير النموذج أو الأوزان أو نصوص التوجيه أو أمثلة التصنيف.

يُعاد استخدام النموذج بين صفحات التطبيق، وتبقى نتائجه المتطابقة مؤقتًا داخل الجلسة وفق القواعد السابقة. تغيير الوصف أو الجهاز أو سياق المراجع يقتضي استدلالًا جديدًا. يُحرر النموذج عند الخروج من الحساب أو بعد عشر دقائق خارج شاشات النموذج.

## الزمن وحدوده

| المرحلة | السلوك |
| --- | --- |
| تنزيل الأوزان وتجهيز القوالب | مرحلة مستقلة واضحة؛ التنزيل الأول نحو 1.1 غيغابايت وقد يستغرق التجهيز دقائق. مهلة مشتركة 15 دقيقة. |
| التصنيف واختيار المرجع | مهلة واحدة لا تتجاوز 45 ثانية، وقد تنخفض لحفظ وقت للتحقق على الخادم. الانتقال بين المهمتين وإعادة المحاولة على CPU لا يجدّدانها. |
| دورة معالجة البلاغ بعد التجهيز | ميزانية 55 ثانية من بدء التحقق من الجلسة، تشمل حفظ البلاغ وتجهيز المراجع والاستدلال والتحقق النهائي. تحجز الواجهة 10 ثوانٍ للتحقق النهائي. |
| تجاوز مهلة النموذج | يُنهى العامل فعليًا، وتُرسل حالة `timeout` إلى المسار المرجعي. لا تُسمى النتيجة نجاحًا للنموذج. |
| تجاوز مهلة الخادم | يتوقف الانتظار برسالة واضحة؛ لا يُدّعى اكتمال التحليل أو حفظه. لا تُعاد طلبات الكتابة تلقائيًا. |

هذه ميزانية انتظار وليست ضمانًا بأن كل جهاز سيُكمل استدلالًا ناجحًا خلال دقيقة. لا تدخل مرحلة التجهيز الأولى في قياس الاستجابة بعد الجاهزية؛ وتقييد المؤقتات في الألسنة الخلفية أو تعليق المتصفح قد يؤخر تحديث الواجهة. إذا قُطع طلب كتابة قد يكون الخادم قد نفّذه؛ تُراجع قائمة البلاغات قبل إعادة الإنشاء.

تُسجّل `preparation_ms` و`inference_ms` منفصلتين عن الزمن الكلي. هذه قياسات يصرح بها المتصفح وليست إثباتًا من الخادم. يبقى ربط النتيجة ببصمة البلاغ وهوية الجهاز والتحقق من المرجع وقواعد الخطورة ومراجعة المختص كما في النسخة السابقة.

## الاستخدام

1. حدّث التطبيق من GitHub وأعد تحميل الصفحة.
2. اضغط «تجهيز النموذج مسبقًا»، وانتظر ظهور «النموذج جاهز»؛ يمكنك إدخال وصف البلاغ أثناء التجهيز.
3. اختر الجهاز وأدخل الوصف ثم نفّذ التحليل. إذا رغبت في التحليل المرجعي مباشرة، استخدم زر «تحليل سريع بالمراجع» أو عطّل خيار النموذج في الصيانة.

## التحقق القابل للإعادة

```bash
cd frontend
npm ci
npm test -- --run
npm run build
npx playwright install chromium
npm run benchmark:prepared
```

يشغّل الاختبار العامل وواجهة الإنتاج فعليًا، ويجهز النموذج مرة واحدة، ثم ينفّذ ستة أوصاف مختلفة بالتناوب بين وجود المراجع وغيابها. يفشل الاختبار إذا لم يصدر اختيار مرجعي صحيح أو إذا بلغ أي طلب 45 ثانية. لا يعتمد على إعادة نتيجة بلاغ مطابق، ولا يختبر زمن شبكة الخادم المصادق عليه. تُحفظ النتائج الفردية وزمن التجهيز وهوية النموذج والمتصفح في `frontend/benchmark-results/prepared-production.json`، وفي مرفق GitHub Actions.

للمقارنة مع بناء سابق: `BENCHMARK_DIST=/path/to/old/dist node scripts/benchmark-prepared.mjs --baseline`. يمكن تحديد `BROWSER_EXECUTABLE` لمسار Chromium و`LLM_MODEL_FILE` لملف GGUF محلي؛ يتحقق الاختبار من SHA-256 للأوزان، ويصرّح باستبعاد تنزيل الإنترنت عند استخدام هذا الخيار. مجموعة المرجع الست اختبار وظيفي وليست تقييمًا سريريًا أو اختبارًا مستقلًا للدقة.

أُضيف تحقق الأداء إلى CI إلى جانب اختبار التصنيف الثابت (40 حالة) واختبارات المرجع. بقيت مقارنة محرك 2.4.0 السابقة متاحة بالأمر `npm run benchmark:llm -- --compare-runtimes`، لكنها لا تُعاد في كل تشغيل لأن التغيير الحالي لا يستبدل المحرك.
