# تشغيل النموذج اللغوي للتصنيف والتوجيه

أضيف تكامل فعلي مع **OpenAI Responses API** إلى مسار صفحة الصيانة:
`POST /api/intelligent-support/analyze-fault`.
يقرأ النموذج وصف البلاغ بالعربية أو الإنجليزية، ويعيد فئة العطل، وخطورته،
وأولويته، ومستواه، وجهة المراجعة المقترحة ضمن JSON محدد البنية.
لا ينشئ النموذج تعليمات إصلاح أو مراجع، ولا يغيّر سجل الجهاز أو يكلّف موظفًا تلقائيًا.
مسار التحليل القديم `/api/fault-reports/analyze` يظل مرجعيًا؛ هذا التكامل يخص صفحة الصيانة والمسار أعلاه.

## التفعيل المحلي

في `backend/.env` أو متغيرات بيئة عملية الخادم:

```dotenv
AI_MODE=openai
OPENAI_API_KEY=YOUR_SERVER_SIDE_API_KEY
LLM_MODEL=gpt-4.1-mini-2025-04-14
LLM_TIMEOUT_SECONDS=30
MAX_TOKENS=1000
```

أعد تشغيل الخادم بعد التعديل. احفظ المفتاح على الخادم فقط؛ لا تضعه في الواجهة،
أو في متغير يبدأ بـ `VITE_`، أو في Git، أو في نص الرسالة الجامعية.
يتطلب الاتصال حساب API مفعّلًا ورصيدًا/صلاحية للنموذج؛ اشتراك ChatGPT وحده ليس مفتاح API.
النموذج الافتراضي مثبت بإصدار محدد لإتاحة توثيق التجربة، ويمكن تغيير `LLM_MODEL`
إلى نموذج متاح للحساب يدعم Responses وStructured Outputs. هذا الاختيار ليس ادعاءً
بأنه النموذج الأفضل للمهمة؛ يلزم تقييم مستقل.

استخدم `AI_MODE=reference` لتشغيل القواعد محليًا دون طلبات خارجية أو رسوم نموذج.
القيمة القديمة `demo` اسم بديل لهذا الوضع؛ `ollama` غير منفذ في هذا التكامل.
`TEMPERATURE` إعداد قديم لا يُرسل ضمن طلب التصنيف الجديد.

## Render وDocker

- **Render:** في إعدادات خدمة الخادم، غيّر `AI_MODE` إلى `openai`، وأضف
  `OPENAI_API_KEY` بوصفه قيمة سرية، وحدد `LLM_MODEL`، ثم أعد نشر الخادم.
  يبدأ `render.yaml` بوضع `reference` حتى تضبط المفتاح عمدًا؛ لا يحتوي ملف النشر مفتاحًا.
  عند إعادة تطبيق Blueprint، راجع قيمة `AI_MODE` كي لا تعود إلى `reference`.
- **Docker Compose:** ضع القيم في `.env` بجانب `docker-compose.yml` ثم شغّل
  `docker compose up -d --build backend`. تمرر Compose القيم إلى حاوية الخادم.
  لا تنشر خرج `docker compose config` لأنه قد يتضمن قيم البيئة السرية.

## التحقق من أن الطلب وصل إلى نموذج حقيقي

من مجلد `backend`، بعد ضبط المفتاح:

```bash
python scripts/smoke_test_llm.py
```

ينفذ الأمر طلبًا واحدًا مدفوعًا حسب حسابك، باستخدام وصف تقني اصطناعي فقط.
ينبغي أن يعيد `status: success` و`model` و`response_id` و`decision` وعدادات الرموز.
يخرج برمز غير صفري عند غياب المفتاح أو فشل الاتصال. لا تعني نجاحاته إثبات الدقة الطبية.
ثم جرّب بلاغًا من صفحة الصيانة؛ يظهر مصدر التصنيف واسم النموذج وجهة المراجعة المقترحة.

## السلوك الفعلي وحدود المخرجات

1. يتحقق الخادم من هوية المستخدم ووجود الجهاز وطول الوصف (10–4000 محرف بعد إزالة
   الفراغات الخارجية). تؤخذ هوية الجهاز من قاعدة البيانات.
2. ينفذ البحث المرجعي والقواعد الحالية، ثم يرسل وصفًا منقحًا وبيانات نوع الجهاز
   والشركة والطراز وحالة اتصال المريض وملخص المرجع المطابق إن وجد.
3. يفصل الطلب تعليمات النظام عن بيانات البلاغ غير الموثوقة. يفرض JSON Schema
   صارمًا، ثم يتحقق من القيم والأنواع مجددًا باستخدام Pydantic.
4. يطبق النموذج تصنيفًا وجهة توجيه مقترحين. تحفظ قواعد الخادم الحد الأدنى للخطورة
   وأولوية التصعيد؛ فلا يخفض النموذج طوارئ اكتشفتها القواعد أو خطورة المرجع المطابق.
   تسجل النتيجة الخام للنموذج والنتيجة النهائية منفصلتين لإمكان المقارنة.
5. تبقى حقول إجراءات الصيانة والمصادر محملة من قاعدة المراجع. عند غياب المرجع
   تظهر رسالة عدم توفره، ويمكن مع ذلك مراجعة التصنيف الأولي وجهة التوجيه.
6. عند غياب المفتاح، أو انتهاء المهلة، أو رفض النموذج، أو فشل التحقق من JSON،
   يعلن النظام الحالة ويستخدم القواعد للمراجعة البشرية. لا يسمي هذه النتيجة نجاح LLM.
   إذا طلب النموذج مزيدًا من المعلومات تظهر حالة `REVIEW_REQUIRED`؛ وتبقى الطوارئ
   أولوية حتى عندما تحتاج تفاصيل البلاغ إلى توضيح.
7. التوجيه **اقتراح جهة مراجعة**، وليس نظام توزيع مهام تلقائيًا أو إشعارًا مرسلًا لفريق.
   لا يُنفذ إجراء طبي أو تغيير في الجهاز بناءً على المخرجات.

لا يجري هذا التعديل استرجاعًا متجهيًا أو تدريبًا/ضبطًا دقيقًا للنموذج، ولا يستبدل
قواعد الشركة المصنّعة. الأوصاف العشوائية التي تتجاوز الحد الأدنى للطول تظل تحديًا
يجب قياسه ضمن التقييم؛ ففحص الطول أو تعليمات النموذج لا يضمنان رفض كل مدخل سيئ.

## الخصوصية والتسجيل

يرسل الوضع `openai` بيانات البلاغ الفنية المنقحة إلى OpenAI. لا يرسل هذا المسار
هوية الحساب أو الرقم التسلسلي أو الموقع؛ يزيل أنماطًا شائعة لأسماء المرضى الموسومة،
وأرقام الملفات، والبريد الإلكتروني وأرقام الهواتف. **هذه معالجة تقريبية وليست
ضمانًا لإخفاء الهوية**؛ يجب أن تكون البلاغات تقنية وخالية أصلًا من المعلومات الشخصية.
يستخدم الطلب `store=false`، وهذا لا يمثل وعدًا بانعدام احتفاظ المزود بالبيانات؛
راجع إعدادات الحساب وسياسة البيانات الرسمية قبل إدخال بيانات فعلية.

يسجل حقل JSON الموجود `AuditLog.classification_result` بيانات:

- نتيجة القواعد قبل الدمج، وقرار النموذج، والنتيجة النهائية وجهة المراجعة.
- المزود، والنموذج المطلوب والنموذج المعاد، و`response_id`.
- `prompt_version` و`prompt_sha256` للتعليمات والمخطط، وبصمة المدخلات المنقحة.
- زمن طلب النموذج وعدادات الرموز، وحالة الفشل العامة إن حدثت، والقيود المطبقة.

لا يتطلب ذلك ترحيلًا لمخطط قاعدة البيانات. لا تسجل المفاتيح أو استجابة الخطأ الخام
من المزود. يظل السجل خاضعًا لصلاحيات المراجعة الموجودة في التطبيق.
درجة المطابقة النصية المعروضة تخص البحث المرجعي؛ ليست احتمالًا معايرًا أو دقة LLM.

## الاختبارات والتقييم البحثي

```bash
# From backend, after installing requirements and initializing the local database
python -m pytest test_llm_triage.py test_alignment_fixes.py test_reference_database.py test_reference_lookup.py test_dashboard_stats.py app/tests -q
# From frontend
npm run build
npm test -- --run
```

اختبارات `test_llm_triage.py` تستخدم `httpx.MockTransport` ولا تتصل بالمزود. تتحقق
من عقد HTTP، وتنقيح المدخلات، ورفض المخرجات غير المطابقة، والتوقف عند المهلة،
ومنع خفض الطوارئ، ودمج المسار مع API وتسجيله، ومنع طلبات النموذج قبل المصادقة.
هذه اختبارات صحة التكامل، وليست قياسًا لأداء نموذج حقيقي. الاختبار الحي يحتاج
تشغيل الأمر السابق بمفتاح متاح؛ لا تُسجل نتائج محاكاة على أنها نتائج نموذج.

لتحديث الرسالة بعد التفعيل: أنشئ مجموعة بلاغات مستقلة عن القواعد، يراجعها مختصون،
وقارن القواعد وحدها وقرار LLM الخام والنتيجة الهجينة على المجموعة نفسها. وثق SHA،
وإصدار النموذج والتعليمات، وتاريخ التجربة، وعدد الحالات، وتوزيع الفئات، وحالات الامتناع
والفشل، ومقاييس التصنيف والتوجيه وزمن الاستجابة. لا تدّع تحسنًا قبل قياسه.
